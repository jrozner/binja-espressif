# xtensa

A dependency-free, `no_std` Rust disassembler for the Xtensa instruction set
as implemented by Espressif's **ESP8266** (Tensilica LX106), **ESP32**
(Tensilica LX6), **ESP32-S2** and **ESP32-S3** (Tensilica LX7) cores.

It is intended as the decoding core of reverse engineering tools such as a
Binary Ninja architecture plugin: instructions decode to an opcode plus
structured operands, with control flow information for building CFGs, and
format like GNU objdump (with `0x`-prefixed addresses).

```rust
use xtensa::{ControlFlow, Isa, Opcode, Operand};

let insn = Isa::ESP32.decode(&[0x36, 0x41, 0x00], 0x400d_0000).unwrap();
assert_eq!(insn.opcode(), Opcode::Entry);
assert_eq!(insn.len(), 3);
assert_eq!(insn.operands(), [Operand::Ar(1), Operand::Imm(32)]);
assert_eq!(insn.to_string(), "entry a1, 32");
assert_eq!(insn.control_flow(), ControlFlow::Sequential);
```

## Coverage

Each `Isa` describes which optional instruction groups and special/user
registers a core implements, and the decoder rejects anything else, just as
the hardware raises an illegal-instruction exception for it.

| | ESP8266 | ESP32 | ESP32-S2 | ESP32-S3 |
|---|---|---|---|---|
| Core ISA, code density (narrow) instructions | ✓ | ✓ | ✓ | ✓ |
| `mul16u/s`, `mull`, `nsa`/`nsau` | ✓ | ✓ | ✓ | ✓ |
| Exceptions, interrupts, debug, TLB, `rer`/`wer` | ✓ | ✓ | ✓ | ✓ |
| Windowed registers (`entry`, `call8`, `retw`, ...) | | ✓ | ✓ | ✓ |
| `muluh`/`mulsh`, `quou`/`rems`/..., `min`/`max`, `sext`, `clamps` | | ✓ | ✓ | ✓ |
| `l32ai`/`s32ri`, `s32nb` | | ✓ | ✓ | ✓ |
| Zero-overhead loops, booleans, MAC16, `s32c1i` | | ✓ | | ✓ |
| Single-precision FPU (incl. `div0.s`, `maddn.s`, ...) | | ✓ | | ✓ |
| ESP32 double-precision assist (`f64*`) and `EXPSTATE` TIE | | ✓ | | |
| LX7 `salt`/`saltu`, `eraccess` register | | | ✓ | ✓ |
| ESP32-S2 dedicated GPIO TIE (`set_bit_gpio_out`, `get_gpio_in`, ...) | | | ✓ | |
| ESP32-S3 PIE: `ee.*` vector instructions (3- and 4-byte), `q0`–`q7` | | | | ✓ |

The presets are `Isa::ESP8266`, `Isa::ESP32`, `Isa::ESP32S2` and `Isa::ESP32S3`.

Custom configurations can be built from `Features` and register tables.

## Using it from a disassembler front end

- `Isa::instruction_length(first_byte)` gives the length (2, 3, or 4 for
  the ESP32-S3 vector format) from the first byte alone.
- `Isa::decode(bytes, address)` decodes one instruction. Branch, jump, call
  and loop targets and `l32r` literal addresses are resolved to absolute
  addresses (`Operand::Target`, `Operand::Literal`).
- `Instruction::control_flow()` classifies branches, jumps, calls (with
  their register window increment), returns, exception returns, loops and
  traps.
- To render text as tokens, print `Instruction::mnemonic()` (which includes
  the register of `rsr.sar`-style instructions) followed by
  `Instruction::text_operands()`.
- `Isa::disassemble(bytes, address)` is an iterator for linear sweeps.

`cargo run --example disasm -- esp32 <file> <base address>` disassembles a
raw binary.

## Testing

The decoder is verified against GNU objdump (binutils 2.45) from
`xtensa-esp-elf` esp-15.2.0_20251204, the toolchain of ESP-IDF v6.1, using its
`esp32`, `esp32s2`, `esp32s3` and `esp8266` configurations, for **every**
possible instruction encoding of each core: about 8.4 million 2- and 3-byte
encodings each, plus all 537 million 4-byte encodings of the ESP32-S3. For the ESP32 and
ESP8266 the results are identical to those of the older esp-2021r2 (ESP32)
and 2020r3 `xtensa-lx106-elf` toolchains.

The encodings come from the objdump sweep itself. They were cross-checked
against Espressif's [xtensa-isa-doc](https://github.com/espressif/xtensa-isa-doc),
the TIE-generated tables in
[xtensa-overlays](https://github.com/espressif/xtensa-overlays), the ESP32-S2
and ESP32-S3 Technical Reference Manuals and the Xtensa ISA Summary
(RI-2021.8) for the LX7 additions. The ESP32-S3 PIE decode table
(`src/pie/esp32s3.rs`) is generated by `scripts/oracle/gen_esp32s3_pie.py`.

`cargo test` needs no toolchain. It checks:

- `tests/exhaustive.rs`: every encoding still decodes to exactly the output
  that was verified against objdump (via a recorded digest);
- `tests/oracle_fixtures.rs`: objdump output sampled across every mnemonic
  and many invalid encodings;
- `tests/corpus.rs`: C code compiled with Espressif's GCC for each chip
  (`tests/corpus`), decoded from the raw bytes and compared with objdump's
  listing;
- `tests/api.rs`: errors, feature gating, control flow and the iterator.

`scripts/oracle/run.sh` downloads the toolchain, runs the exhaustive
comparison, and regenerates all of the fixtures above. A nightly CI workflow
runs it, along with `tests/exhaustive.rs`, and fails if objdump disagrees on
any encoding or if the committed fixtures are stale; regular CI runs the
remaining tests on every push and pull request.

Where the reference objdump has quirks, the comparison accounts for them
(see `tests/common/objdump.rs`): libisa decodes unknown encodings as its
first opcode (`lsi` on ESP32, `excw` on LX106), the ESP8266 configuration
prints `rer`/`wer` without operands and has no names for the `CONFIGID`
registers, and objdump prints addresses without a `0x` prefix.
